# 空白図鑑

日本語版Wikipediaで、暮らしに関わる重要概念が**まだらに**欠けている場所を、検証済みの形で集めた図鑑。

- 公開中: **https://kuhaku.caprer.co.jp**

## 主張の範囲

このサイトが言うのは **「Wikipedia日本語版に、この概念の独立記事を確認できなかった」** であって、
**「日本語にこの情報が存在しない」ではない**。コトバンク・日本語論文・技術記事・書籍には書かれているかもしれない。

言わないこと:

- 「日本語にこの情報が存在しない」
- 「日本は知的に遅れている」（データに反する。日本語版のほうが厚い概念も実在する）
- 「日本語版Wikipediaは質が低い」
- 「英語版のほうが正しい／完全である」
- 「Wikipedia編集者がこの穴を埋めるべき」
- 「リダイレクトや統合は誤りである」（独立記事にしない編集判断には正当な理由がある）
- 文字数の少なさを品質評価と混同すること

## なぜ検証レイヤーが要るのか

「英語版にあって日本語版に無い」を Wikidata の sitelink 差分で機械的に出すと、
**実測で55%が誤り**だった（2026-09-08、学問分野25件・生活分野11件の2回で再現）。

内訳:

- 記事が普通に実在する（sitelink が繋がっていないだけ）
- 上位記事へのリダイレクトで実質的に包含されている（例: 核医学 → 放射線医学）
- 別概念に吸収されている（例: 詩学 → 詩学 (アリストテレス)）
- 日本に存在しない制度なので記事が無いのが自然

したがって、このリポジトリの中身は「差分の抽出」ではなく **「差分の検証」** にある。

### 実装中に踏んだ罠（すべて実物）

1. **全文検索を選定に使うと壊れる**
   `パラソーシャル関係` → 「バーチャルYouTuber」を比較対象に選び、文字比 0.73 と出た。
   `スクリーンタイム` → 「24時間テレビ」を選び、文字比 2.75 と出た。
   → 全文検索は**候補の材料**にのみ使い、比較対象には絶対に選ばない。

2. **Wikidata のラベル・別名も典拠にならない**
   `満腹感`（「食」へ転送）を選んで文字比 7.72、`栄養強化` に対して「栄養補助食品」を選ぶ、など。
   → 自動選定は **ja sitelink が実在する場合のみ**。それ以外は人間が同一概念だと確認して昇格させる。

3. **バイト数比較は使えない**
   日本語はUTF-8で1文字≒3バイト。バイト比較は日本語版と英語版の分量比を約3倍過大に算出する。
   さらに wikitext のバイト数はテンプレートやマークアップを含むので本文量とは別物。
   → 本文の**文字数**で測る。

4. **附録節を数えると格差を過大に見せる方向へ偏る**
   英語版は Further reading / External links が長い。除外しないと自分の主張に有利な方へ数字が動く。
   → 附録節は**その子節ごと**除外する。

5. **取得失敗を「記事が無い」と取り違えてはいけない**
   → 1件でも取得に失敗したら、その概念の比較全体を無効にする。

## 判定（5値）

| 判定 | 意味 |
|---|---|
| 欠落 | 独立記事も、上位・隣接記事内の実質的な記述も確認できない |
| 薄い | 独立記事はある。英語版で扱われ日本語版で確認できない論点を**人手で特定した** |
| 実質包含 | 独立記事は無いが、上位・隣接記事の中に定義がある |
| 該当なし | この調査でいう空白にはあたらない。観測した3指標のいずれでも日本語版が上回った |
| 判定不能 | 別名不明・粒度が違う等で判定できない |

### 判定規則

**「欠落」に confidence: high は付けない。**
不在は原理的に完全証明できない。確認した隣接記事の revision ID と使った検索語をすべて記録した上で、
最大 medium とする。実際、high を付けた「欠落」のうち**2件が後から実質包含だと判明した**。

**実質包含は「単一の隣接記事が概念を定義している」場合のみ。**
用語を節見出しや同義語として挙げるだけでは足りない。
複数の記事を読者が合成しなければ概念全体にならない場合は実質包含としない。
対応する独立記事が存在するなら、隣接記事に分散があっても「薄い」を覆さない。

**キーワード検査は本文限定で行う。**
wikitext のテンプレート／ナビボックスに現れるリンクは記述ではない。

**粒度の異なる記事同士の文字数比を示して「薄い」と断じない。**
日本語版が上位概念を扱っている場合など、比較が成立しないときは判定不能を使う。

**文字数が少ないだけでは「薄い」にしない。**
必ず本文を読み、英語版で扱われていて日本語版の記事では確認できない論点を1つ以上特定する。

### 「無い」に見えるものの5つのパターン（実例）

| パターン | 実例 |
|---|---|
| 完全に無い | 道徳的傷害（en 21,129字。隣接9記事すべてに痕跡なし） |
| 記事はあるが別物 | スクリーンタイム（en=Q28130149 / ja は Wikidata 項目なしの Apple 機能の記事） |
| 日本語版のほうが厚い | 過剰診断（ja 12,368字 > en 11,219字、脚注ドメイン 49 vs 1） |
| **別記事の1文としてだけ存在** | 育児スタイル（en 48,396字 → 「ダイアナ・バウムリンド」354字の中の1文） |
| 記事はあるが定義文だけ | 温熱快適性（en 35,062字 → ja 114字） |

## 観測値の定義

いずれも**観測値であって品質評価ではない**。統合して「情報量」と呼ばない。

- **本文文字数** — レンダリング済み平文から附録節（とその子節）を除き、空白を除いた文字数
- **節数** — 最上位（`==`）の節の数。附録節を除く
- **脚注に直接書かれた外部URLのドメイン数** — wikitext の `<ref>...</ref>` 内のURLのみ。
  Wikimedia・短縮URL・SNS・識別子リゾルバ（doi.org 等）を除いた eTLD+1 のユニーク数
- **最終更新** — 取得した revision のタイムスタンプ

### 既知の限界

- `{{sfn}}` `{{harvnb}}` `{{efn}}` `{{reflist|refs=}}` 形式の脚注は拾えない。
  これらを多用する記事ではドメイン数が**系統的に過少計上**になる。度合いは `template_footnote_markers` で確認できる。
- eTLD+1 は同梱の簡易サフィックス表で求めている。完全な Public Suffix List ではないため、
  `github.io` や `blogspot.com` のようなホスティングは1発行元に潰れる。
- 「ドメイン数」は発行主体の独立性を保証しない。同一発行元が複数ドメインを持つこともある。

## 再現方法

依存パッケージは無い。Python 3.11 以降の標準ライブラリだけで動く
（`pip install` を要求しないのは、第三者が検証しやすいことを最優先しているため）。

```bash
python3 -m pipeline.collect concepts/living.toml
```

出力される証拠バンドル（`data/evidence/*.json`）には、第三者が同じ結果に到達するための情報が入っている:

- 各ページの **revision ID** と wikitext / 平文の SHA-256
- Wikidata エンティティの `lastrevid`
- 発行したすべての **リクエストURL**、HTTPステータス、応答の SHA-256
- 入力ファイル（concepts/*.toml）の SHA-256
- 算出規則のバージョン（`calc_version`）と Python のバージョン
- 候補タイトルが**どこから来たか**（sitelink / ラベル / 別名 / 人手 / 全文検索）
- 適合性フィルタの判定と根拠

API応答の生データは `data/raw/<run_id>/<応答のSHA-256>.json.gz` に保存される。
ハッシュだけでは後日同じ応答を得られないため、応答そのものを残している。

## 対象の選び方（MVP対象適合性フィルタ）

暮らし編で扱うのは、次の**いずれか**を満たす概念に限る。

- **a** 国に依存しない人間行動・健康・生活上の概念
- **b** 日本国内での発生・利用を、独立した日本語資料2件以上で確認できる
- **c** 海外制度だが、日本居住者の生活に直接影響する

> これは「日本語版Wikipediaにその記事が**必要か**」を裁定する基準ではない。
> 今回の暮らし編で**扱う対象を選ぶ編集基準**である。

## ディレクトリ

```
concepts/       対象概念の定義（人が書く）
judgments/      5値判定の記録。追記型で、訂正は履歴として残る（人が書く）
pipeline/       証拠収集。判定は一切しない
data/evidence   証拠バンドル
data/raw        API応答の生データ（gzip）
site/build_site.py  データ → 公開サイト（HTML/CSV/JSON）
site/public/    生成物
site/wrangler.jsonc Cloudflare Workers の静的配信設定
```

## 公開サイト

```bash
./run.sh check     # 生成 + 文面チェック
./run.sh deploy    # 生成 + 文面チェック + 配信 + 配信後の確認
```

**文面チェックを通らないものは配信しない。** 主張範囲を超えないことでこの調査は成り立っているので、
その規律を目視に頼らずコード（`site/lint_copy.py`）にしてある。禁止表現、記事全体の分量として
書いた数値と観測値の照合、不在断定に探索範囲の限定が添えてあるか、などを検査する。

公開表示では断定語を使わない。内部の判定値はそのまま残し、表示だけを置き換える。

| 内部判定 | 公開表示 |
|---|---|
| 欠落 | 確認できず |
| 薄い | 論点に差がある |
| 実質包含 | 別記事の中にある |
| 判定不能 | 比較できない |
| 該当なし | 日本語版が上回る |
| confidence: medium | 探索済み・断定保留 |
| confidence: high | 根拠を引用できる |

**文字数を比例図示しない。** 英語1字と日本語1字は情報量が同じではないため、
面積や枚数に換算して並べると比較可能性の誇張になる。
図示するのは言語によらず数えられる量（節数・脚注内の外部参照ドメイン数）だけで、
文字数は数値と注記にとどめる。

**CSV/JSON の全行に判定と検証状態を持たせる。** 数値だけを取り出せる表は作らない。
不在は `0` ではなく空欄にする（0字の記事があると誤読されるため）。

## この repository について

生成物（`site/public/`）も含めて置いてある。「何を公開したか」を後から差分で追えるようにするため。

`pipeline/wikiclient.py` の User-Agent は当初、連絡先として個人のメールアドレスを含めていた。
公開にあたりプロジェクトのURLに差し替えた（2026-09-14）。
Wikimedia の User-Agent 方針は連絡先としてURLでも満たせる。
過去の証拠バンドルに記録されていた文字列も同じ理由で差し替えている。取得した応答そのものには影響しない。
